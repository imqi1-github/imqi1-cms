# 生成更新日志（changelog）

## 目标
读「最近一批提交的真实改动」，写成面向访客、可导入后台的更新日志条目，写入根目录 `changelogs.json`。

**关键原则：看 git diff 的内容，不重复提交信息。** 提交信息是给开发者的技术速记（常含 `<scope>/bug 描述`），要把它翻译成用户能感知的成果条。必须逐个 `git show` 看实际改动、必要时 Read 改动的源码文件，理解「对访客/后台用户而言多了什么、变了什么」。

## 一、确定要处理的提交范围（三选一）

**模式 0（手动指定 N 条，用户调用时给了参数）**
```bash
# 参数 N 是「回溯多少条提交」，例如 /changelog 12 → 最近 12 条
git log -N --pretty=format:"%h|%ad|%s" --date=format:"%Y-%m-%d %H:%M" HEAD
```
从这段输出里取要处理的那批提交。

**模式 1（默认，靠 changelogs.json 游标往前推）**
1. 取根目录 `changelogs.json` 里**最大的** `createTime` 作游标 = 上一次生成日志锚定的最新提交时间（取最大值可覆盖整个文件——记录即使乱序/手工补录也能找到真正的锚点）：
```bash
cursor="$(node -e "const a=require('./changelogs.json');let m='';for(const r of a){const t=r.createTime||'';if(t>m)m=t}console.log(m)")"
```
2. **按提交 hash 精确定位交界边界，再取「边界之后」的提交**。这样既不重复上一批（上一批最后一条被排除），也不会漏掉与游标同一分钟但更晚的新提交——旧写法 `--after <分钟> + grep -v` 会用「分钟串」一刀切，把同分钟的新提交一起吞掉（丢归「覆盖不全」，把边界外的同分钟提交删掉归「含上次内容」，两头都错）：
```bash
# 上一批的最后一条 = git log 里第一个「提交时间分钟 == 游标」的提交
boundary="$(git log --pretty=format:'%H|%ad' --date=format:'%Y-%m-%d %H:%M' HEAD \
  | awk -F'|' -v c="$cursor" '$2==c {print $1; exit}')"
if [ -n "$boundary" ]; then
  # boundary..HEAD = 严格在边界之后的全部提交（线性历史等价按时间递增；同分钟更晚的新提交被正确保留，边界本身被排除）
  git log "${boundary}..HEAD" --pretty=format:"%h|%ad|%s" --date=format:"%Y-%m-%d %H:%M"
else
  # 游标对应不到提交（历史被改写/导入，无同分钟提交）→ 回退时间阈值；此时无法精确排除，尽量只丢交界那一分钟的提交
  git log --pretty=format:"%h|%ad|%s" --date=format:"%Y-%m-%d %H:%M" --after "$cursor" \
    | grep -vE "^[0-9a-f]+\|${cursor}\|"
fi
```

**模式 2（changelogs.json 为空/无记录，或游标对应不到提交时）——回退最近 3 天**
```bash
git log --since "3 days ago" --pretty=format:"%h|%ad|%s" --date=format:"%Y-%m-%d %H:%M"
```

> 若「模式 1 过滤后为空」= 自上次生成以来没有新提交 → 直接告诉用户「无新提交」，不要写文件。

## 二、读真实改动（不是提交信息）

对上面筛出的每个提交做两件事，再按需展开源码：

```bash
git show --stat <hash>          # 改了哪些文件、规模
git show <hash>                 # 完整 diff
git diff <最早那条提交>^..HEAD  # 该批整体 diff（看合并后的用户可见效果）
```

- 重点看 `app/`（前端页面/组件/composable）、`server/`（Nitro API/后端）、`shared/`（跨端逻辑）、`mini/`（小程序）、`prisma/`（数据层）的变化。
- 对拿不准「用户感受到什么」的改动，用 Read 打开被改文件里关键的 `.vue`/`.ts` 片段确认（例如这是加了搜索逻辑、改了缓存面板、还是换了个字体）。**宁可读代码，也别凭提交信息猜。**
- 提交里常见的 `docs:`（README/注释）基本对用户不可见，**通常不写**，或合并成一条「其他」；`chore:`（部署/配置/构建）只有影响部署/运维才写，否则略过——「让用户看得到」是筛选标准。

## 三、提炼成条目

### type 取值（唯一合法集合，见 `shared/changelog.ts`）
`功能 | 优化 | 修复 | 删除 | 设计 | 新增 | 其他`
对照参考：
- `feat:` 全新能力 → **新增**；若属于「扩展现有模块/新增一个子模块」也可用 **功能**
- `perf:` / 性能 / 提速 → **优化**
- `fix:` → **修复**
- 视觉/组件间外观 → **设计**
- 下线/删除功能 → **删除**
- 纯粹的 `docs/deps/内部 chore/refactor` 且用户感知不到 → **其他**（或省略）
- 不确定 → **其他**（`normalizeChangelogEntries` 会把非法 type 回退成「其他」，但别靠它）

### 风格（必须对齐根目录 `changelogs.json` 现有条目）
- 一条 = 一个用户可感知的改动。**多提交构成一个功能时合并成一条**（如「搜索增强」可能跨多个 commit）。
- 中文，密实、信息密度高；用「」引组件/接口/参数名；括号补技术细节或影响；分号串联相关点。
- 尽量点名具体物：组件名、接口路径、字段/参数、文件名（如「新增 /api/heatmap 接口」「TravelMap 初始化 zooms 上限固定 20」「JetBrainsMono 无空格家族名」）。
- 描述成果，不复述错误/内部机制（「修复 X 导致的 BUG」→ 写成「修复了……于是能……」）。但关键原因可保留（例如「内存会话跨 bundle 不共享」这种务必写清）。
- 例（截自现有文件）：
  - `新增 | 关于页站点统计新增「发布热力图」：按天聚合已发布文章与已审核评论数，支持按分类/标签维度筛选（新增 /api/heatmap 接口与 ActivityHeatmap 组件，星期标签/月份标签随年份切换）`
  - `修复 | 修复旅行地图切换视图后地图空白、放大后 POI 文字消失的问题：缩放上限改为 createCluster 建聚合时同步设置，避免「地图无点却允许深缩放」的窗口；底图 zooms 上限固定 20 保住高德 POI 标注层`

### 校验
每条 `value` 非空；`type` 属于上面的合法集合。全部条目至少一条有内容才写。

## 四、写入 changelogs.json

`changelogs.json` 是一个**数组**，元素为记录：
```json
{ "createTime": "2026-08-22 21:43", "entries": [ { "type": "新增", "value": "..." } ] }
```

1. `createTime` = **本批最新一条提交的提交时间**（这样下次运行能无缝锚定游标，不重复）：
   `git log -1 --format=%ad --date=format:"%Y-%m-%d %H:%M"`
2. **`changelogs.json` 是「待导入」暂存文件，只保留本批新记录，不携带旧纪录**（旧条目入库后即失效；若连同旧记录一起保留，重复导入会产生重复行）。故用 Write 整体覆盖——数组里只有本批这一条记录（`createTime` + `entries`），旧纪录全部丢弃，数组长度恒为 1。保持既有缩进风格（记录对象内部属性、条目对象单行紧凑），结构沿用上一节 JSON 示例。
3. **写前确认两件事，都满足才覆盖：**
   - **非空**：本批有内容才写；若「模式 1 过滤后为空」且文件已有记录 → 按第一节提示「无新提交」，**不动文件**（先读现有文件再决定，别把文件覆盖成空数组）。
   - **不重叠**：新 `createTime` > 现有文件里的 `createTime`（模式下自动成立，边界已排除上一批）。若新 `createTime` ≤ 现有 `createTime`（模式 0 手动指定 N 回溯到更早的提交才会出现），说明本批与已入库记录重叠 → 提示用户，**不要覆盖**（否则游标倒退、下次又重复处理）。

## 五、发布提示（必须告知）
写完后提醒用户到后台导入，文案类似：
> 已更新根目录 `changelogs.json`（覆盖为仅含本批 1 条记录 / N 个条目，旧纪录已清除）。去后台 **`/admin/changelogs` → 「导入 JSON」→ 选择根目录 `changelogs.json` → 导入** 即可入库，前台 `/changelogs` 会按月展示。
> ⚠️ 导入会**新增** DB 记录；若重复导入会产生重复行，需要重导可先在后台删除对应记录。

## 边界
- 只读 git、只改 `changelogs.json`；**不要**改数据库、不跑 `migrate`、不写其他文件。
- 遵守公开接口白名单/CSRF 等仓库硬性约定（本 skill 不涉写接口，仅提示导入）。
- 不确定某提交是否该写时，向用户复述并让其定夺，别擅自吞掉或放大。
